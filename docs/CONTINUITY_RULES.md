# Codex 项目持续开发与长期记忆规范

你正在维护一个长期持续开发的软件项目。

从现在开始，本项目采用 **“源码即交付、文档即记忆”** 的工作方式。不要依赖聊天记录作为唯一上下文。所有重要信息必须同步写入项目文件，以确保即使开启新的对话、上下文被截断或模型发生变化，也能够仅通过项目文件恢复完整开发状态。

---

# 一、最高优先级原则

1. 所有实际修改必须落实到源码文件中。
2. 所有重要设计、决策、接口、配置、问题、TODO、构建方式必须落实到文档文件中。
3. 不允许仅在聊天回复中说明重要信息而不写入项目文档。
4. 每次任务完成后，必须更新项目文档。
5. 每次交付时，必须确保“源码 + 文档”均完整输出。
6. 不要假设未来的对话仍然保留当前聊天上下文。
7. 项目文件是唯一可信的长期记忆来源。
8. 如果聊天内容与项目文档冲突，以最新明确的用户要求为最高优先级，并同步修正文档。

---

# 二、项目长期记忆文件

如果以下文件不存在，请创建；如果已经存在，请持续维护，禁止重复创建多个同类文件。

必须维护：

```text
/docs/PROJECT_STATE.md
/docs/ARCHITECTURE.md
/docs/DECISIONS.md
/docs/CHANGELOG.md
/docs/TODO.md
/docs/BUILD.md
/docs/README_DEV.md
/docs/API.md
/docs/KNOWN_ISSUES.md
/docs/SESSION_HANDOFF.md

README.md
```

---

## 1. PROJECT_STATE.md

这是最重要的项目记忆文件。

必须记录：

- 当前项目目标
- 当前版本
- 已完成功能
- 未完成功能
- 当前目录结构
- 核心模块说明
- 当前技术栈
- 当前构建环境
- 当前依赖
- 已知问题
- 当前正在开发的功能
- 下一步计划
- 用户明确提出但尚未完成的要求
- 重要文件位置
- 关键配置
- 项目当前可以运行到什么程度
- 最近一次修改内容

每次完成开发任务后必须更新。

未来任何新会话开始工作之前，必须首先读取：

1. `README.md`
2. `docs/PROJECT_STATE.md`
3. `docs/ARCHITECTURE.md`
4. `docs/DECISIONS.md`
5. `docs/TODO.md`
6. `docs/KNOWN_ISSUES.md`
7. `docs/BUILD.md`
8. `docs/SESSION_HANDOFF.md`

然后再开始修改代码。

不要仅依赖聊天记录恢复项目状态。

---

## 2. ARCHITECTURE.md

记录：

- 总体架构
- 模块划分
- 数据流
- 核心类
- 核心接口
- 数据库结构
- 网络层
- UI 架构
- 后台任务
- 平台适配层
- 关键依赖关系

架构发生变化时必须同步修改。

---

## 3. DECISIONS.md

记录所有重要技术决策。

每项至少包含：

- 日期
- 问题
- 可选方案
- 最终选择
- 选择原因
- 潜在缺点
- 后续影响

禁止未来开发时无理由推翻已经记录的技术决策。

如果需要修改已有决策，必须新增一条决策记录说明原因。

---

## 4. CHANGELOG.md

记录每次实际代码修改。

格式至少包括：

- 日期
- 版本
- 新增
- 修改
- 修复
- 删除
- 兼容性变化

---

## 5. TODO.md

维护真实待办事项。

分类：

- P0 必须完成
- P1 高优先级
- P2 普通功能
- P3 优化项
- Future 后续规划

完成项目后及时标记完成状态。

---

## 6. BUILD.md

必须保证一个新的开发者只阅读该文件，就能够：

- 安装开发环境
- 安装依赖
- 编译项目
- 运行项目
- 调试项目
- 打包 Release
- 找到最终产物

需要记录：

- 操作系统要求
- SDK
- JDK
- 编译器
- IDE
- Gradle / Maven / npm / cargo 等版本
- 环境变量
- 构建命令
- Debug 命令
- Release 命令
- 签名方式
- 输出目录

---

## 7. API.md

记录：

- 内部接口
- 外部 API
- 数据结构
- 参数
- 返回值
- 错误码
- 权限
- 平台特有 API

如果项目不存在 API，也需要说明当前没有对外 API。

---

## 8. KNOWN_ISSUES.md

记录：

- 已确认 Bug
- 设备兼容问题
- 暂时无法实现的功能
- 系统限制
- 第三方平台限制
- 需要真机测试的问题
- 临时解决方案

禁止把未解决问题隐藏在聊天记录里。

---

## 9. SESSION_HANDOFF.md

这是每次对话/开发任务结束时必须更新的交接文档。

必须记录：

- 本次任务目标
- 本次完成内容
- 本次修改的主要文件
- 本次新增文件
- 本次删除文件
- 本次构建结果
- 本次测试结果
- 当前未解决问题
- 当前阻塞点
- 下次继续开发时应该先做什么
- 下一步推荐顺序
- 需要特别注意的上下文
- 用户最新明确要求

原则：

> 新会话只要读取此文件和项目核心文档，就应该能无缝继续。

每次任务结束时更新，允许覆盖旧内容，但历史变更必须保留在 `CHANGELOG.md` 中。

---

# 三、每次开发任务开始前必须执行

开始任何代码修改之前：

1. 阅读当前项目源码结构。
2. 阅读 `PROJECT_STATE.md`。
3. 阅读 `TODO.md`。
4. 阅读 `DECISIONS.md`。
5. 阅读 `KNOWN_ISSUES.md`。
6. 阅读 `SESSION_HANDOFF.md`。
7. 判断用户当前要求与现有架构是否冲突。
8. 如果冲突，以最新用户要求为准，并同步更新相关文档。
9. 不得因为聊天上下文中没有某项信息，就直接假设项目没有实现该功能。

---

# 四、每次开发任务完成后必须执行

代码修改完成以后，不要立刻结束。

必须完成：

1. 检查修改过的代码。
2. 尽可能执行构建。
3. 尽可能执行测试。
4. 检查是否有编译错误。
5. 检查是否有明显未实现代码。
6. 更新 `PROJECT_STATE.md`。
7. 更新 `CHANGELOG.md`。
8. 更新 `TODO.md`。
9. 更新 `SESSION_HANDOFF.md`。
10. 必要时更新 `ARCHITECTURE.md`。
11. 必要时更新 `DECISIONS.md`。
12. 必要时更新 `API.md`。
13. 必要时更新 `KNOWN_ISSUES.md`。
14. 必要时更新 `BUILD.md`。
15. 检查 `README.md` 是否仍然准确。

最终回复必须说明：

- 本次完成内容
- 修改了哪些主要文件
- 测试/构建结果
- 当前已知问题
- 下一步尚未完成内容

---

# 五、完整交付要求

当我说：

- “打包项目”
- “完整输出”
- “导出全部源码”
- “给我完整项目”
- “最终交付”
- “生成项目压缩包”
- “把项目全部给我”

或表达类似意思时：

必须生成一个完整压缩包。

例如：

```text
ProjectName-full-source.zip
```

压缩包必须包含：

- 全部源代码
- Gradle/Maven/npm/cargo 等构建文件
- 配置文件
- AndroidManifest 或对应平台配置
- assets
- resources
- 数据库定义
- 脚本
- 测试代码
- docs 完整目录
- README.md
- LICENSE（如果项目已有）
- 示例配置
- 项目状态文档
- 构建说明

不得只提供修改过的部分文件。

不得只提供 diff。

不得只提供聊天中的代码片段。

不得遗漏隐藏在子目录中的源码。

---

# 六、禁止打包的内容

除非我明确要求，否则不要包含：

```text
build/
.gradle/
node_modules/
IDE 临时缓存
.idea/cache
编译中间文件
无意义日志
临时文件
本机绝对路径相关缓存
```

但是必须保留项目正常构建所需的：

- Gradle Wrapper
- `gradlew`
- `gradlew.bat`
- `gradle/wrapper/*`
- `package.json`
- lock 文件
- 配置模板
- ProGuard/R8 配置
- Android Manifest
- Version Catalog
- 构建脚本

---

# 七、敏感信息处理

禁止把以下真实信息写入交付包：

- 密码
- API Secret
- Access Token
- 私钥
- 签名密码
- OAuth Secret
- 用户个人数据

使用：

```text
.env.example
```

或其他模板代替。

如果项目依赖某个 Secret，必须在 `BUILD.md` 中说明如何配置，但不要填写真实 Secret。

---

# 八、可恢复开发要求

最终项目必须做到：

即使未来开启一个完全新的 Codex 对话，只需要把这个项目目录交给新的 Codex，然后告诉它：

> 读取项目文档并继续开发。

它就应该能够理解：

- 项目是什么
- 已经实现了什么
- 当前架构
- 为什么采用当前方案
- 还有什么没有实现
- 当前有哪些 Bug
- 如何编译
- 如何测试
- 下一步应该做什么

如果做不到这一点，说明项目文档还不完整。

---

# 九、文档不能只存在于聊天中

任何可能影响后续开发的信息，只要满足以下任意一项，就必须写入项目文档：

- 用户明确需求
- 架构决定
- API 设计
- 数据库设计
- 平台限制
- 系统兼容问题
- 尚未解决的问题
- TODO
- 临时方案
- 构建方式
- 发布方式
- 测试结果
- 第三方服务配置
- 未来开发计划

原则：

> 聊天用于交流，文件用于长期记忆。

聊天回复不能代替项目文档。

---

# 十、最终自检

每次重大修改或项目打包前，都必须检查：

```text
[ ] 源码是否完整
[ ] 文档是否完整
[ ] PROJECT_STATE.md 是否为最新
[ ] TODO.md 是否为最新
[ ] CHANGELOG.md 是否为最新
[ ] SESSION_HANDOFF.md 是否为最新
[ ] KNOWN_ISSUES.md 是否为最新
[ ] BUILD.md 是否可以让陌生开发者完成构建
[ ] 是否遗漏必要配置文件
[ ] 是否包含不应该提交的缓存文件
[ ] 是否泄露 Secret
[ ] 项目是否可以脱离当前聊天继续开发
```

只有完成以上检查后才算任务完成。

---

# 十一、对我的交付方式

只要运行环境允许创建文件：

不要让我手动复制代码。

直接生成文件。

如果我要求完整项目：

直接生成 ZIP 压缩包供我下载。

如果能够生成 APK、EXE、IPA、Docker Image、JAR 或其他最终产物，也应同时提供对应构建产物。

同时保留完整源码包。

任何时候都不能用“源码太多所以省略”作为理由。

不要用：

- “其余代码保持不变”
- “略”
- “省略未修改部分”
- “和之前一样”

来替代完整交付。

完整交付必须是真实、完整、可恢复的项目文件。

---

# 十二、持续执行

以上规则不是一次性要求。

这是整个项目生命周期中的长期规则。

后续每一次：

- 功能开发
- Bug 修复
- 架构调整
- 重构
- 发布
- 打包

都必须继续遵守。

如果未来的某条临时指令没有明确取消这些规则，则继续执行这些规则。

---

# 十三、新会话推荐启动指令

以后开启新的 Codex 对话时，可以直接输入：

```text
先完整读取 README.md 和 docs 目录，重点读取：

- docs/PROJECT_STATE.md
- docs/ARCHITECTURE.md
- docs/DECISIONS.md
- docs/TODO.md
- docs/KNOWN_ISSUES.md
- docs/BUILD.md
- docs/SESSION_HANDOFF.md

这些文件是项目的长期记忆和当前状态来源。

不要依赖旧聊天记录，不要重新设计已经确定的架构。

读取完成后，先总结：
1. 当前项目状态
2. 已完成功能
3. 未完成功能
4. 已知问题
5. 当前开发优先级
6. 推荐下一步

然后再根据我的新要求继续开发。

所有新的重要信息必须继续同步写回项目文档。
```

---

# 十四、核心原则

最终原则只有一句：

> **聊天用于交流，文件用于长期记忆；源码和文档必须始终一起交付。**
